Signed targeted re-encodes now fetch R2-stored corpus scopes with the organization's corpus read credentials (`R2_CORPUS_READ_ACCESS_KEY_ID` and `R2_CORPUS_READ_SECRET_ACCESS_KEY`), which are meant to be read-only; the workflow relies on the secret names, not on the key's scope. Only the provision-fetch step holds any R2 credential. An ad hoc run missing either credential value stops before the production-signing gate, so a signing review isn't spent on a run that couldn't fetch its pinned corpus. That check tests that both values are present, not that they authenticate. Queue dispatches skip it, and their fetch step still refuses a lock-pinned corpus without both values. The fetch step asks for the credentials only for a lock-pinned corpus; a lockless (git-history) pin reads its provisions from the checkout and needs none.
