`axiom-encode ci` supports validate-rulespec pin 92ccb0f2, which rulespec-us calls since 4c9aeadd. It recognizes the caller's resolver that also reads `axiom_compose_ref`, runs the pre-check's ProgramSpec shape check with `guard-programs-root` (and checks that its interpreter has the pinned PyYAML), and reproduces the isolated dependency layout: an exclusive dependency root under the run's `RUNNER_TEMP`, exported to repository pytest as `AXIOM_DEPENDENCY_ROOT`/`AXIOM_DEPENDENCY_STAGE`, with an empty staging directory left in the workspace and no `_axiom`, so the rules checkout's Cargo inputs no longer reach the engine build. The root's engine, canonical rulespec-us and composer entries are real directories, the latter two fresh clones at their pins, as CI's are. When the caller pins a composer, ci checks the pin against `.axiom/workflow-toolchain.toml`, authenticates the `--compose-path` checkout, requires CI's uv version, builds the composer runtime with uv (reading committed project configuration, not user or system configuration) and the encoder pin's own `provision_axiom_compose_runtime.py`, and passes it, with `--rulespec-dependency-root` for repositories other than rulespec-us, to the waiver audit (now `--json`), validation and companion tests, as CI does. New flag: `--compose-path`. The composer build's uv cache is the fresh `setup-uv-cache` CI's step gets, never a directory a committed file names (a `cache-dir` setup-uv finds in the rules checkout fails resolution; `no-cache` is honored, its temporary cache inside the run); siblings the composer reaches by path are built from fresh clones, never the developer's checkouts; and the corpus release object is never fetched or written through a symlinked `releases` path.
