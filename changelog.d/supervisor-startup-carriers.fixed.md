The signing supervisor now refuses more Python startup carriers in its trusted trees, including the ones CPython's path configuration reads under the supervisor's own `-I -S` start, before the trusted bootstrap runs. Names match in any case, on files and directories alike: `._pth` and `pybuilddir.txt` join `pyvenv.cfg`, `.pth`, `.egg-link` and `__editable__*`, and every `sitecustomize`/`usercustomize` form (package directory, `.pyc`, extension module) joins the `.py` one. Positional rules join them. The supervisor refuses a `python3*.zip` entry, file or directory, in `lib/` or `lib64/` of the interpreter's directory or of any ancestor of it, up to `/` (the stdlib zip slot `sys.path` lists first, which path configuration also looks for above the runtime root), and requires every existing `lib/` or `lib64/` above the runtime root to meet the runtime's owner and mode rules. It refuses a `Modules` entry, the build-tree marker, directly in the runtime root, `bin/`, `lib/` or `lib64/` (path configuration reads it in `bin/` on Linux and in the runtime root on macOS builds such as CPython 3.13.13), and a `lib` or `lib64` entry directly in `lib/` or `lib64/`, where CPython 3.14.0 starts its prefix search. The interpreter must sit directly in the runtime's `bin/`, and every entry in `bin/` must be a regular file. `scripts/provision_verification_supervisor.py` purges the same forms case-insensitively, removes a stdlib zip that is a directory, keeps a `python3*.zip` data file anywhere other than directly in `lib/`, `lib64/` or `PLATLIBDIR`, and refuses an interpreter at the prefix root. Name and position rules cannot see a changed stdlib byte, an extension module beside a stdlib source, cached bytecode that runs in place of its source, or a new module in an earlier `sys.path` entry that shadows a later one; a pinned runtime-tree digest checked before exec would close all four.
