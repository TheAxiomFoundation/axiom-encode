# Local contribution admission

Status: contributor decision recorded; implementation and deployment pending. Tracks
[#1628](https://github.com/TheAxiomFoundation/axiom-encode/issues/1628),
with the setup and experiment record in
[#1622](https://github.com/TheAxiomFoundation/axiom-encode/issues/1622).
[Max's decision on #1629](https://github.com/TheAxiomFoundation/axiom-encode/pull/1629#issuecomment-5732652158)
selects **enrolled producers**. The [notary design v33](notary-admission-design.md)
was signed off and merged through
[#1507](https://github.com/TheAxiomFoundation/axiom-encode/pull/1507) on
2026-09-18. This work plan scopes that direction at the contributor
interface; it does not replace the protocol, complete its §9 deployment
preconditions, or enable runtime admission.

## Contributor outcome

A team contributor uses their own Codex subscription with the supported
encoder on an enrolled supervised runtime, submits generated RuleSpec files
and authenticated lineage in a PR, and receives an admission verdict over
those exact files. The organization does not regenerate the contribution.
Producer and actor keys stay on the supervised runtime host; the separate
notary key stays in the external typed signer. Codex credentials never enter
GitHub Actions or the submitted evidence bundle.

Admission requires v33's digest-bound receipt-approver signature and
protected workflow authorization. Passing a local check or approving a PR
does not replace them. Adding model reviewers is outside this work plan;
the approved notary design places LLM review outside its admission
authority. The verifier profile and required gates remain protected policy.

The billing direction is already recorded in the
[subscription-first directive](https://github.com/TheAxiomFoundation/.github/issues/39#issuecomment-5006531271).
The [notary charter](https://github.com/TheAxiomFoundation/axiom-encode/issues/1192)
places generation on operator-controlled compute and admission in a separate
verification and signing path. The enrollment work below turns that policy
into an onboarding procedure; there is not yet an enrollment command or
enabled US notary path supplied by this PR.

## Reproduction and root cause

The [unsigned contributor experiment, rulespec-us#1350](https://github.com/TheAxiomFoundation/rulespec-us/pull/1350),
used encoder 0.2.1764 at the
[same commit the target pinned](https://github.com/TheAxiomFoundation/rulespec-us/blob/84f860af059294e5577fdbd8bf6a7818f47cb472/.axiom/workflow-toolchain.toml).
The local run reported `standalone_validated` for
`us/regulation/42/435/145/b`. Its
[CI job](https://github.com/TheAxiomFoundation/rulespec-us/actions/runs/34509691232/job/102980592699)
then failed at `Reject manual RuleSpec changes` after about 4h44m:

```text
Manual RuleSpec changes are not allowed.
- us/regulations/42-cfr/435/145/b.test.yaml changed without a matching .axiom/encoding-manifests manifest
- us/regulations/42-cfr/435/145/b.yaml changed without a matching .axiom/encoding-manifests manifest
```

The earlier workflow steps passed. Later YAML validation, companion tests,
proof validation and oracle-coverage checks were skipped. The experiment
demonstrates the manifest blocker, not that those later CI checks passed.

The changes that produced this behavior were:

| Change | Effect |
| --- | --- |
| [Issue #63](https://github.com/TheAxiomFoundation/axiom-encode/issues/63) | Requested provenance a local agent could not forge using a shared HMAC secret. |
| [PR #1108](https://github.com/TheAxiomFoundation/axiom-encode/pull/1108), July 11, 2026 | Removed local HMAC signing and `sign-applied-files`; required v5 Ed25519 apply manifests through the trusted broker. |
| [PR #1135](https://github.com/TheAxiomFoundation/axiom-encode/pull/1135), July 14, 2026 | Added the external production signer with Actions-only production-key use. Local-dev mode generates a temporary key that does not match the production trust root. |
| [rulespec-us#397](https://github.com/TheAxiomFoundation/rulespec-us/pull/397), June 12, 2026 | Restored the generated-file guard after consolidation; later encoder pins enforce the newer manifest contract. |

The current `targeted-signed-reencode` workflow generates from a citation.
Its `repair_run_id` accepts context from an earlier protected run; it is not
a general intake for a contributor's existing draft. An encoder version is
one required dependency identity, not a signing credential or proof that a
particular file was generated by that build.

## Decision: enrolled team producers

The selected path follows
[the #1506 decision](https://github.com/TheAxiomFoundation/axiom-encode/issues/1506#issuecomment-5322219757):
generation records must authenticate as emissions of an enrolled supervised
runtime. Open candidate intake is out of scope; contributors outside the
team require a future explicit policy decision. Repository membership,
write access, a self-selected key, and installing a root-owned verification
runtime do not establish producer enrollment.

This distinction explains experiment #1350. It demonstrated personal-Codex
generation under a verification-only supervisor; it did not enroll a
producer, emit authenticated notary-era lineage, or invoke a notary.
The existing guard rejected the missing v5 apply manifest. The replacement
path must supply v33 lineage and notary acceptance through its own domain;
it must not bypass the guard or sign a v5 manifest over submitted bytes.
Earlier unsigned experiments remain diagnostic evidence, not retroactively
authenticated generation records.

## Enrollment work packages

These are implementation deliverables, not commands that already work.
Use the roles, closed schemas, registry, and administrative transitions in
v33; enrollment must not introduce an alternate trust file or signing path.

### 1. Authenticate and authorize a producer

The team operator and supervised-runtime host custodian supply an enrollment
record identifying the operator, host/runtime identity, reviewed runtime
build and configuration, intended lane, and producer public-key fingerprint.
The record must include evidence connecting the key to that runtime's
protected emission service; proof of key possession alone does not establish
that boundary. The implementation defines the evidence collection and
verification procedure for review.

Max, the administrative-key custodian named in v33 §11, authenticates this
enrollment evidence and authorizes the trusted registry entry. Initial keys
enter through the §8 ceremony and §6.2 genesis; subsequent additions use
§6.4's administrative transition under predecessor-state roots. The
normative public-key registry is `.axiom/notary/keys.json` (§5), not an
organization variable or a file the contributor can self-authorize. The
enrollment record supports that authorization and is not a new verifier
schema or substitute for the registry. Name the host custodian and all
other required key custodians in the ceremony record before enrollment is
activated.

Acceptance evidence: enrollment rejects evidence that fails to connect the
hosted key to the reviewed runtime. Once enrolled, its eligible generation
record verifies under the producer role in the lane's effective registry;
an unknown key refuses. Onboarding and the supervised emitter establish and
enforce the runtime-to-key binding. V33's notary authenticates the registered
signer and its declared `runtime_identity`; the role/key registry contains no
runtime-identity mapping for the notary to check independently. A GitHub
write-role check alone must never produce an enrolled status.

### 2. Establish the supervised runtime boundary and emit lineage

The runtime implementation must bind the registered identity to the reviewed
encoder, pinned Codex executable, and configured emission service. Document
and test the OS/process controls that keep producer signing capability from
agent-controlled code and ensure it records actual supervised emissions,
rather than signing arbitrary uploaded files. A root-owned verification-only
installation is a prerequisite building block, not evidence that these
producer controls exist.

Export v33 §2.2 generation records over exact before/after blob digests and
modes, bound to the lane and epoch, with runtime/model/CLI identity and prompt
digests. Include all required v33 per-draw fields (`draw_set_id`, `sampling`,
`independence`, `source_capture`) in the closed schema. Their well-formedness
is required, but their values remain producer declarations; signatures do
not establish statistical independence or trusted wall-clock ordering.
Later recorded corrections follow §2.3's separate actor and correction-review
signatures. The normal repair path remains fix the encoder and regenerate.

Acceptance evidence: a supported personal-Codex run produces byte-bound,
schema-valid lineage without model credentials in the export. Modified bytes,
cross-lane/epoch replay, and attempts to obtain producer signatures over
arbitrary files fail. Unsupported runtime or CLI identity is reported before
generation where the required identity can be checked locally.

### 3. Provision and retain keys on the correct hosts

The supervised-runtime host custodian provisions distinct producer and actor
keys there; those keys never leave that host (§11). Contributor tooling uses
the supervised signing operations without exporting private keys into a
shell, checkout, model context, or CI. The external typed signer holds the
notary key. The correction-review and receipt-approver keys are two distinct
hardware keys with named custodians; Max holds the administrative key.
The §8 ceremony records custody, fingerprints, rotation, revocation, and
recovery for each role and establishes §5's total key separation, including
the retained legacy apply/eval roots and the corpus-release role.

Acceptance evidence: role-separation tests reject aliased keys; the documented
host-bound signing operation works without exporting a key; producer/actor
capabilities cannot authorize a notary receipt or administrative transition.
CI and the external notary signer receive no personal Codex credentials.

### 4. Revoke, rotate, and recover enrollment

The host custodian's incident procedure disables a compromised emission
service and identifies affected keys and outstanding candidates. Max
authorizes registry removal or rotation using §6.4's transition protocol;
the old administrative roots authorize the change, never the proposed new
key. Activation and publication follow the finalized-chain rules in §7.

Document and test when revocation becomes effective at the lane, how
unfinalized or superseded candidates are invalidated and resubmitted, and
how the operator learns to stop using old evidence. After the transition is
effective, new candidates signed only by the removed producer key must
refuse under the new base registry. Already finalized historical artifacts
remain verifiable under their recorded predecessor roots; do not rewrite
history or treat producer timestamps as proof that a signature predates
compromise. Recovered hosts require renewed boundary verification and
administrative authorization before generating eligible new evidence.

## Implementation boundaries

Implementation must use the approved notary protocol, key separation and
publication rules. The following work packages describe the contributor
interface to that system, rather than a replacement protocol:

1. **Onboarding and local evidence export, axiom-encode.** Implement the four
   enrollment packages above and publish the supported toolchain and
   registry-bound public verification material. Export only the
   explicitly defined candidate and evidence files, bound to exact module/test
   bytes, eligible lineage, and source/toolchain identities. Never archive
   the contributor's home, credential files, environment or unfiltered workspace. Diagnostic
   output must distinguish locally validated, submitted and admitted states.
2. **Immutable intake and verification, axiom-encode plus a dedicated protected
   notary workflow.** Follow #1507's prohibition on reusable workflows for
   Job 1 and the trusted job. Allow an unadmitted candidate to enter verification without a
   pre-existing organization apply signature. Pin the complete candidate
   commit/tree and protected base, dependencies, source release, waiver policy
   and verifier profile. Run cheap structural and evidence refusals before
   the expensive waiver audit. A report-only check cannot satisfy the
   existing required admission check.
3. **Protected authorization and signing, notary deployment.** Follow #1507's
   recomputation, approval, external-signing and publication boundaries.
   Treat candidate-provided reports as untrusted proposals. Candidate code
   never receives signing authority. Verification does not repair or
   regenerate files; required changes return to the contributor as findings.
   A new acceptance statement uses the approved distinct domain and key;
   legacy v5 manifests retain their generator-produced meaning.
   The trusted side recomputes the structural and lineage invariants; #1507
   treats candidate-side gate outcomes as declarations, not independently
   re-executed results. Its accepted candidate-gate-compromise residual must
   remain explicit in the signed claim and contributor documentation.
4. **Downstream enforcement, shared workflow and pilot RuleSpec repository.**
   Verify admission against the exact subject and protected policy. A changed
   head/base invalidates stale acceptance. Preserve or deliberately migrate
   required-check identity and source-App binding under the approved design;
   never satisfy branch protection with an unrelated report-only job.

The notary design currently pilots `rulespec-nz`; an end-to-end US fix
additionally requires an explicit US deployment decision and consumer changes.
The axiom-encode PR alone cannot establish organization environments, enroll
keys, configure external services or change another repository's required
checks. Those are tracked deployment prerequisites, not completed by docs.

## Delivery order and what can be tested now

1. **This documentation PR:** record the selected enrollment contract and
   work packages; review their consistency with v33. Documentation checks
   establish that this plan is reviewable, not that local drafts are admitted.
2. **Implementation and isolated fixtures:** deliver the verifier, producer
   enrollment/emission tools, and notary integration against the acceptance
   cases below. [#1511](https://github.com/TheAxiomFoundation/axiom-encode/pull/1511)
   is the initial verifier-core work, not an onboarding or signing service.
3. **Operator deployment and pilot:** satisfy every v33 §9
   precondition, complete the custody ceremony, and activate the `rulespec-nz`
   pilot. Report-only verification supplies no merge authority.
4. **Explicit US rollout and live experiment:** deploy the approved US
   consumer changes and enroll the contributor's runtime before rerunning
   a small encoding. Capture the generated file digests, eligible lineage,
   protected verification and approval, notary receipt/finalization, and
   accepted US check. Confirm no model generation occurred in CI and no
   submitted file was silently changed. A new missing-manifest failure under
   the old US guard is not a test of this path.

## End-to-end acceptance tests

These are required future implementation tests, not claims about checks
implemented by this proposal. Use fixture identities and mock model output
for automated tests; use one separately authorized real-subscription smoke
test for the contributor experience. Model mocks must not replace the actual
candidate binding, verification, refusal, signing and downstream guard logic.

| Scenario | Required result |
| --- | --- |
| Enrolled team runtime using personal Codex, eligible evidence, and v33 approval | Exact candidate admitted without organization model generation or exported host/notary private keys. |
| Team member with write access but no enrolled runtime | Enrollment prerequisite reported; write access does not authorize lineage or signing. |
| Contributor outside the team | Refused by this rollout; open intake requires a separate future policy decision. |
| Missing evidence or unsupported toolchain | Cheap, actionable refusal before the multi-hour audit or any signing operation. |
| Changed module or test bytes after evidence generation | Evidence binding fails. |
| Enrollment evidence fails to connect the hosted key to the reviewed runtime | Enrollment refuses; a registered signer's runtime declaration is not an independently verified runtime measurement. |
| Self-selected key or unsigned generation declaration | Refused as authenticated lineage; no open-intake fallback. |
| Producer key removed by an effective registry transition | New candidates requiring that key refuse; rotation and historical verification follow predecessor-state roots. |
| Producer, actor, notary, review, approval, administrative, or legacy keys alias across roles | Registry/custody validation refuses under v33's total separation rule. |
| Candidate changes workflow, verifier, waiver policy or trust roots | Ordinary admission refuses; dedicated administrative transition required. |
| Candidate fails compilation, source grounding, tests or another required gate | No acceptance statement; fixes are returned without silent repairs. |
| Report claims valid lineage/coverage but trusted recomputation disagrees | Refusal; candidate-written structural claims cannot authorize signing. |
| Required gate declaration is missing or has an unacceptable outcome | Refusal under the protected verifier profile; accepted declarations do not prove independent gate execution. |
| Replayed receipt for another repo, source, head or base | Refusal. |
| Candidate moves after approval or before publication | Stale acceptance cannot satisfy admission for the new candidate. |
| PR code attempts to access signing authority or contributor Codex credentials | No such capability is available to the job. |
| Report-only verification passes without protected authorization | PR remains unadmitted. |
| Existing valid v5 artifact is verified | Its original semantics are preserved; it is not reinterpreted as a notary statement. |

LLM reviewer scores are not a substitute for any test above. Likewise, the
current oracle-coverage classification step does not execute numerical
oracle comparisons. The approved verifier profile must say which actual
oracle executions are required; marking an output comparable or covered by
tests is not evidence of numerical parity.
