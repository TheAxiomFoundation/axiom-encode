# Local contribution admission

Status: proposal, not an implemented admission path. Tracks
[#1628](https://github.com/TheAxiomFoundation/axiom-encode/issues/1628),
with the setup and experiment record in
[#1622](https://github.com/TheAxiomFoundation/axiom-encode/issues/1622).
The admission design remains subject to
[#1507](https://github.com/TheAxiomFoundation/axiom-encode/pull/1507)'s
sign-off and deployment prerequisites. This document adds a contributor
acceptance contract; it does not replace that protocol or authorize signing.

## Contributor outcome

A contributor uses their own Codex subscription with the supported local
encoder, submits generated RuleSpec files and evidence in a PR, and receives
an admission verdict over those exact files. The organization does not
regenerate the contribution. The contributor never receives organization
signing keys and never uploads Codex credentials to GitHub.

Normal maintainer review and approval may gate admission. Passing a local
check is evidence for the review process, not authority to merge. A model
reviewer is not required by this contributor proposal; the existing notary
design places LLM review outside its admission authority. The final verifier
profile and its required gates remain protected policy.

The billing direction is already recorded in the
[subscription-first directive](https://github.com/TheAxiomFoundation/.github/issues/39#issuecomment-5006531271).
The [notary charter](https://github.com/TheAxiomFoundation/axiom-encode/issues/1192)
places generation on operator-controlled compute and admission in a separate
verification and signing path. Neither document by itself supplies an
enrollment procedure for a new contributor.

## Reproduction and root cause

The [unsigned contributor experiment, rulespec-us#1350](https://github.com/TheAxiomFoundation/rulespec-us/pull/1350),
used encoder 0.2.1764 at the
[same commit the target pinned](https://github.com/TheAxiomFoundation/rulespec-us/blob/84f860af059294e5577fdbd8bf6a7818f47cb472/.axiom/workflow-toolchain.toml).
The local run reported `standalone_validated` for
`us/regulation/42/435/145/b`. Its
[CI job](https://github.com/TheAxiomFoundation/rulespec-us/actions/runs/34509691232/job/102980592699)
then failed at `Reject manual RuleSpec changes` after about 4h44m:

```text
Manual RuleSpec changes are not allowed.
- us/regulations/42-cfr/435/145/b.test.yaml changed without a matching .axiom/encoding-manifests manifest
- us/regulations/42-cfr/435/145/b.yaml changed without a matching .axiom/encoding-manifests manifest
```

The earlier workflow steps passed. Later YAML validation, companion tests,
proof validation and oracle-coverage checks were skipped. The experiment
demonstrates the manifest blocker, not that those later CI checks passed.

The changes that produced this behavior were:

| Change | Effect |
| --- | --- |
| [Issue #63](https://github.com/TheAxiomFoundation/axiom-encode/issues/63) | Requested provenance a local agent could not forge using a shared HMAC secret. |
| [PR #1108](https://github.com/TheAxiomFoundation/axiom-encode/pull/1108), July 11, 2026 | Removed local HMAC signing and `sign-applied-files`; required v5 Ed25519 apply manifests through the trusted broker. |
| [PR #1135](https://github.com/TheAxiomFoundation/axiom-encode/pull/1135), July 14, 2026 | Added the external production signer with Actions-only production-key use. Local-dev mode generates a temporary key that does not match the production trust root. |
| [rulespec-us#397](https://github.com/TheAxiomFoundation/rulespec-us/pull/397), June 12, 2026 | Restored the generated-file guard after consolidation; later encoder pins enforce the newer manifest contract. |

The current `targeted-signed-reencode` workflow generates from a citation.
Its `repair_run_id` accepts context from an earlier protected run; it is not
a general intake for a contributor's existing draft. An encoder version is
one required dependency identity, not a signing credential or proof that a
particular file was generated by that build.

## Decision: who can produce eligible generation evidence?

The following are distinct contracts. Choose one before implementing or
enabling contributor admission; this proposal selects neither implicitly.

1. **Enrolled producer:** the contributor enrolls a supervised runtime and
   producer key. Generation records authenticate the output as an emission
   of that producer. This matches the direction of
   [the #1506 decision](https://github.com/TheAxiomFoundation/axiom-encode/issues/1506#issuecomment-5322219757).
   Onboarding must specify who authenticates the producer, how the runtime
   boundary is established, how key custody is protected, and how keys are
   revoked. A contributor-created key and a root-owned local directory are
   not sufficient by themselves to establish an organization-trusted producer.
2. **Open candidate intake:** any contributor can submit files and declarations;
   admission relies on independent verification and explicit maintainer
   authorization. Their generation declarations remain untrusted provenance.
   This requires an explicit decision on the acceptance claim and a change
   or extension to #1506/#1507's eligible-lineage requirement. A passing check
   or maintainer click must not silently convert self-declared generation into
   authenticated runtime evidence.

Both can use a personal Codex subscription. Only the second provides intake
without prior producer enrollment. Neither permits bypassing the guard,
distributing production signing keys, or signing a v5 generator manifest
over arbitrary submitted bytes.

## Implementation boundaries

Implementation must use the approved notary protocol, key separation and
publication rules. The following work packages describe the contributor
interface to that system, rather than a replacement protocol:

1. **Onboarding and local evidence export, axiom-encode.** Publish the supported
   toolchain and publicly obtainable verification roots. Export only the
   explicitly defined candidate and evidence files, bound to exact module/test
   bytes and source/toolchain identities. Never archive the contributor's
   home, credential files, environment or unfiltered workspace. Diagnostic
   output must distinguish locally validated, submitted and admitted states.
2. **Immutable intake and verification, axiom-encode plus a dedicated protected
   notary workflow.** Follow #1507's prohibition on reusable workflows for
   Job 1 and the trusted job. Allow an unadmitted candidate to enter verification without a
   pre-existing organization apply signature. Pin the complete candidate
   commit/tree and protected base, dependencies, source release, waiver policy
   and verifier profile. Run cheap structural and evidence refusals before
   the expensive waiver audit. A report-only check cannot satisfy the
   existing required admission check.
3. **Protected authorization and signing, notary deployment.** Follow #1507's
   recomputation, approval, external-signing and publication boundaries.
   Treat candidate-provided reports as untrusted proposals. Candidate code
   never receives signing authority. Verification does not repair or
   regenerate files; required changes return to the contributor as findings.
   A new acceptance statement uses the approved distinct domain and key;
   legacy v5 manifests retain their generator-produced meaning.
   The trusted side recomputes the structural and lineage invariants; #1507
   treats candidate-side gate outcomes as declarations, not independently
   re-executed results. Its accepted candidate-gate-compromise residual must
   remain explicit in the signed claim and contributor documentation.
4. **Downstream enforcement, shared workflow and pilot RuleSpec repository.**
   Verify admission against the exact subject and protected policy. A changed
   head/base invalidates stale acceptance. Preserve or deliberately migrate
   required-check identity and source-App binding under the approved design;
   never satisfy branch protection with an unrelated report-only job.

The notary design currently pilots `rulespec-nz`; an end-to-end US fix
additionally requires an explicit US deployment decision and consumer changes.
The axiom-encode PR alone cannot establish organization environments, enroll
keys, configure external services or change another repository's required
checks. Those are tracked deployment prerequisites, not completed by docs.

## End-to-end acceptance tests

These are required future implementation tests, not claims about checks
implemented by this proposal. Use fixture identities and mock model output
for automated tests; use one separately authorized real-subscription smoke
test for the contributor experience. Model mocks must not replace the actual
candidate binding, verification, refusal, signing and downstream guard logic.

| Scenario | Required result |
| --- | --- |
| Supported local generation using personal Codex usage, with eligible evidence and required maintainer approval | Exact candidate admitted without organization model generation or contributor access to signing keys. |
| New contributor lacking repository-write access | Documented intake works; dependencies and public roots are obtainable, or any enrollment prerequisite is reported before generation. |
| Missing evidence or unsupported toolchain | Cheap, actionable refusal before the multi-hour audit or any signing operation. |
| Changed module or test bytes after evidence generation | Evidence binding fails. |
| Self-selected key or forged generation declaration | Refused as authenticated lineage; any open-intake acceptance uses only its separately approved, narrower claim. |
| Candidate changes workflow, verifier, waiver policy or trust roots | Ordinary admission refuses; dedicated administrative transition required. |
| Candidate fails compilation, source grounding, tests or another required gate | No acceptance statement; fixes are returned without silent repairs. |
| Report claims valid lineage/coverage but trusted recomputation disagrees | Refusal; candidate-written structural claims cannot authorize signing. |
| Required gate declaration is missing or has an unacceptable outcome | Refusal under the protected verifier profile; accepted declarations do not prove independent gate execution. |
| Replayed receipt for another repo, source, head or base | Refusal. |
| Candidate moves after approval or before publication | Stale acceptance cannot satisfy admission for the new candidate. |
| PR code attempts to access signing authority or contributor Codex credentials | No such capability is available to the job. |
| Report-only verification passes without protected authorization | PR remains unadmitted. |
| Existing valid v5 artifact is verified | Its original semantics are preserved; it is not reinterpreted as a notary statement. |

LLM reviewer scores are not a substitute for any test above. Likewise, the
current oracle-coverage classification step does not execute numerical
oracle comparisons. The approved verifier profile must say which actual
oracle executions are required; marking an output comparable or covered by
tests is not evidence of numerical parity.
